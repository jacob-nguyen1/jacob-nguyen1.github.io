Bare-metal RC car

An IR-remote car on an STM32F446 where I wrote every peripheral driver from the reference manual, without the HAL. I started it because I wanted to actually understand timers, DMA, and interrupts instead of calling library functions that hide them. The code is on GitHub.

What it does

It decodes NEC commands from a cheap IR remote (forward, reverse, pivot, and nine speed levels) and drives four TT motors through two DRV8833 H-bridges at 20 kHz PWM. Wheel encoders feed a PI loop that holds a target speed, and a button on the remote switches between open and closed loop. If the remote goes quiet for 200 ms, the motors stop.

How the timers are split up

Almost everything ends up being a hardware timer:

TIM3 + DMA1 Stream 4Input capture on the IR receiver. DMA copies each edge timestamp into a 66-entry buffer at 1 µs resolution, so the CPU never polls.
TIM4Four channels of 20 kHz PWM to the motor drivers.
TIM2Input capture on both wheel encoders. It's 32-bit, so slow wheels don't overflow it.
TIM6, TIM7Watchdogs. One throws away half-received IR packets, the other stops the motors after 200 ms of silence.
SysTickRuns the PI loop at 100 Hz and a stopped-wheel check at 1 kHz.
USART2printf over the ST-Link for debugging.

Bugs worth writing down

DMA was eating my interrupt flag

Once DMA was capturing the IR edges, my timer interrupt stopped firing completely. The watchdog never got reset, so the car timed out constantly. The capture flag CC1IF clears when CCR1 is read, and the DMA reads CCR1 on every edge, so the flag was gone before the CPU could see it.

I fixed it by mapping a second capture channel (IC2) onto the same input pin. Every edge now sets two flags: DMA consumes CC1IF, and the CPU gets CC2IF, which nothing else touches.

Motors wouldn't spin below 77% duty

At 20 kHz the motors had a huge deadband, which left the PI loop almost nothing to work with. I was pulsing IN1 and holding IN2 low, which puts the DRV8833 in fast decay during the off-time. The coil current collapsed between every pulse, so most of each on-time went to building it back up. Holding IN2 high and pulsing an inverted signal on IN1 switches the chip to slow decay instead. The current keeps circulating between pulses, and the deadband dropped to 33%.

The car would coast to a stop and never restart

Speed came from the time between encoder edges. When a wheel stopped, the edges stopped too, so the last reading (fast) stayed there forever. The controller thought the car was cruising and kept the duty too low to overcome static friction. Now a 1 kHz check compares TIM2's counter to the last capture, and if 200 ms pass with no edge, the wheel is treated as stopped.

The first move after boot lasted three times too long

The timer prescaler and auto-reload registers are buffered: a new value doesn't take effect until the next update event. So the first timeout ran with the reset value of ARR (655 ms instead of 200 ms). Setting the UG bit at the end of timer init forces an update and loads the new values immediately.

Smaller ones

  • A uint8_t speed parameter wrapped −50 into 206, which meant full throttle instead of stop. It's an int32_t now, clamped in the driver.
  • Disabling a DMA stream mid-transfer sets its transfer-complete flag, which sent my reset interrupt into a loop. I now stop the timer's DMA requests before touching the stream.
  • A printf inside an interrupt made a race condition disappear, because the UART delay covered up the timing problem. I toggle a GPIO and watch it on the scope instead.
  • Header pins pushed into the motor driver boards without solder gave floating outputs. They worked once they were soldered.
