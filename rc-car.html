Bare-metal RC Car

An IR-remote car where I wrote every peripheral driver from the reference manual, with no HAL and no Arduino. I started it to actually understand timers, DMA, and interrupts instead of calling library functions that hide them.

Source on GitHub

What it does

  • Decodes NEC IR remote commands (forward, reverse, pivot, 9 speed levels).
  • Drives four TT motors with 20 kHz PWM through two DRV8833 H-bridges.
  • Holds a target wheel speed with a PI loop fed by wheel encoders, with a remote button to switch between open and closed loop.
  • Stops the motors if it loses the remote signal for 200 ms.

How it's put together

Almost everything is a hardware timer. Here's how I split them up:

PeripheralJob
TIM3 + DMA1 Stream 4Input capture on the IR receiver. DMA copies each edge timestamp into a 66-entry buffer at 1 MHz resolution, so the CPU never polls.
TIM44-channel 20 kHz PWM to the motor drivers.
TIM2Input capture on the left and right wheel encoders (it's 32-bit, so slow wheels don't overflow it).
TIM6 / TIM7Watchdogs: one resets a half-received IR packet, the other kills the motors after 200 ms of silence.
SysTickRuns the PI loop at 100 Hz and a stopped-wheel check at 1 kHz.
USART2printf over the ST-Link for debugging.

The drivers (GPIO, Timer, PWM, DMA, IR, UART) each get their own .c/.h pair with typed enums and config structs, and tuning values live in one config.h.

Bugs that taught me the most

1. The DMA was eating my interrupt flag

When DMA captured the IR edges, my timer interrupt stopped firing completely, so the watchdog never got reset and the car timed out constantly. It turns out the capture flag CC1IF clears when CCR1 is read. The DMA reads CCR1 on every edge, so it cleared the flag before the CPU ever saw it.

Fix: I mapped a second capture channel (IC2) onto the same input pin with CC2S. Now every edge sets two flags: DMA consumes CC1IF, and the CPU gets its own CC2IF that nothing else touches.

2. Motors wouldn't spin below 77% duty

At 20 kHz the motors had a huge deadband, which left the PI loop almost no range to work with. I was pulsing IN1 and holding IN2 low, which puts the DRV8833 in fast decay during the off-phase. The coil current collapsed between every pulse, so most of each on-phase went to building it back up.

Fix: I held IN2 high and pulsed an inverted PWM on IN1, which switches the chip to slow decay. The current keeps circulating between pulses, and the deadband dropped from 77% to 33%.

3. The car would coast to a stop and never restart

Speed was measured from the time between encoder edges. When a wheel stopped, the edges stopped too, so the last measured speed (fast) stayed in place forever. The controller thought the car was cruising and kept the PWM too low to overcome static friction.

Fix: a 1 kHz check in SysTick compares TIM2->CNT to the last capture. If 200 ms pass with no edge, the wheel is marked stopped and the loop drives it back up.

4. The first move after boot lasted 3× too long

Timer PSC and ARR are preloaded (shadow) registers. Writing them doesn't take effect until the next update event, so the first timeout ran with the reset value of ARR (655 ms instead of 200 ms).

Fix: TIMx->EGR |= TIM_EGR_UG at the end of timer init forces an update so the new values load immediately.

5. Smaller ones worth remembering

  • A uint8_t speed parameter silently wrapped -50 into 206 (full throttle instead of stop). It's an int32_t now, clamped at the driver.
  • Disabling a DMA stream mid-transfer sets its transfer-complete flag, which sent my reset ISR into a loop. I now stop the timer's DMA requests before touching the stream.
  • A printf in an ISR made a race condition disappear, because the UART delay hid the timing bug. I use GPIO toggles on the scope for timing now.
  • Push-in header pins on the motor drivers gave floating outputs. They work once they're actually soldered.
